# 设备角色、配对同步与宠物端看板 — 设计文档

日期：2026-06-11
状态：待评审

## 0. 背景与范围

宠记（PetNote）当前是纯本地、无账号的宠物照护 App（Flutter，Android / iOS / 鸿蒙三端，数据层 sembast + shared_preferences）。本设计覆盖五项需求：

1. 首次启动流程添加「这台设备为谁服务？」角色选择（爱宠 / 主人）。
2. 宠物端与主人端配对、选择服务的宠物；主人端「我的 → 设备」管理已配对设备；无账号自动多端数据同步。
3. 宠物端常驻不掉线，全新「大块标签贴纸」看板 UI，右上角设置可切换 App 模式。
4. 爱宠页副标题重构（它 / 它们 的照护档案）。
5. 爱宠页「远程视频」胶囊按钮，弹出「视频通话」/「先看看它」两个选项。

### 已确认的决策（与用户对齐）

- 同步通道：**自建云端中继**，部署在用户自有 VPS。
- 服务端语言：**Dart**（shelf + WebSocket），与 App 共享协议模型。
- 视频实体功能（WebRTC 真实接入）**留下期**；本期完成入口 UI 与信令协议定义，不接 RTC。视频方案确定为 WebRTC 开源自建（flutter_webrtc + 自建信令 + STUN/自建 coturn），无付费 SDK。
- 宠物端三端都做；iOS 做不到后台常驻就只做前台常亮。
- 分期：原一、二期合并为本期（角色选择 + 配对同步 + 宠物端看板与保活 + 副标题 + 视频入口）。

## 1. 设备角色与首次启动流程（需求 1）

- 新增 `DeviceRole` 枚举：`owner` / `pet` / `undecided`，由 `AppSettingsController` 持久化（shared_preferences，key `device_role_v1`）。
- `PetFirstLaunchIntro`（lib/app/pet_first_launch_intro.dart）现有 3 页之后新增**第 4 页「这台设备为谁服务？」**，两个大卡片选项：
  - **主人**：role 落盘为 `owner`，显示现有「那我们开始吧 / 先看看宠记」按钮，走现有 onboarding；
  - **爱宠**：role 落盘为 `pet`，直接进入配对流程页。
- 重启行为：
  - `role == pet`：直接进宠物端（未配对 → 配对页；已配对 → 看板），不再显示 intro；
  - `role == owner`：走现有逻辑；
  - `role == undecided` 且已有本地数据（老用户升级）：自动视为 `owner`，不打扰；
  - `role == undecided` 且无数据：照常显示 intro（含新角色页）。

## 2. 配对与无账号多端同步（需求 2）

### 2.1 同步架构：单写者快照同步

主人端是唯一权威数据源：

- `PetNoteStore` 维护一个**数据集级递增版本号**（pets / todos / reminders / records 任一变更即 +1）；快照直接复用现有备份模型 `PetNoteDataState`（已有完整 JSON 编解码），整体加密推送——数据量小，不做按表/按记录拆分；
- 主人端监听 store 变化，节流（~2s）后将加密快照推送至服务器；
- 宠物端通过 WebSocket 订阅 `householdId`，收到推送 → 解密 → 经现有 `replaceAllData` 写入本地副本 → 看板刷新；
- 宠物端的写操作（如勾选待办完成）不直接改数据，以 **action 消息**回传：主人端在线即时应用并推回新快照；离线则进服务器队列，上线后重放。宠物端本地乐观显示。

放弃的备选：记录级双向 LWW 同步（为未来多主人端设计，本期复杂度不值）、CRDT（过度设计）。

### 2.2 配对协议

1. 主人端「我的 → 设备」页点「添加设备」→ 请求服务器生成 **6 位配对码**（5 分钟有效）；
2. 宠物端输入配对码 → 服务器撮合双方；
3. 双方以配对码 + 服务器返回的随机盐通过 HKDF 派生**共享密钥**（用于同步数据的 AES-GCM 加密）；
4. 建立 `householdId`（首次配对时创建）+ 双方 `deviceId`、设备名；
5. 主人端推送首份全量快照 → 宠物端从宠物列表中**选择服务哪只宠物**（`servedPetId`，可在主人端设备管理页改绑）。

### 2.3 端到端加密

同步数据经 AES-GCM（key 来自 2.2 派生）加密后上传，服务器日常只存密文与版本号。威胁模型说明：配对码经服务器撮合，**恶意服务器理论上可在配对窗口截获配对码并派生密钥**——本方案面向「用户自建、自管的服务器」，防护目标是磁盘密文泄露与传输安全（TLS 之上叠一层），不防服务器本身恶意；如未来开放第三方服务器，再升级为 PAKE（如 SPAKE2）。隐私文案微调：intro 第 3 页「所有数据均安全保存在本地」→「数据仅在你的设备与你自己的服务器间加密同步」（仅在启用同步后语义变化，措辞实施时定稿）。

### 2.4 服务端与代码结构

```
PetNote/
  packages/petnote_sync_protocol/   # 纯 Dart：消息模型、加密封装、版本协议（App 与 server 共享）
  server/                            # Dart shelf + WebSocket 中继
```

服务器职责：配对码撮合、按 household 存储表快照密文（落盘持久化）、action 队列、设备在线状态、（预留）视频信令消息转发。部署：Dockerfile + docker-compose（编排含可选 coturn，本期仅写配置不接入），TLS 由用户反代（Caddy/nginx）。

### 2.5 设备管理（主人端）

`me_page.dart` 新增「设备」入口卡片 → 设备列表页：

- 列表项：设备名、服务的宠物、在线状态、最近同步时间；
- 操作：重命名、改绑宠物、解绑；
- 页内：同步服务器地址配置、生成配对码入口、「将本机切换为宠物端」入口。

共享密钥等敏感信息复用现有 `AiSecretStore` 的 method channel 安全存储模式（新增 `SyncSecretStore` 或扩展现有通道）。

## 3. 宠物端看板与保活（需求 3）

### 3.1 看板 UI

`role == pet` 时 `PetNoteApp` 的 home 直接换成全新 `PetDeviceDashboard`（不进现有四 tab 壳层）：

- 大块「标签贴纸」式小组件铺满屏幕（模拟现实标签）：今日待办、最近提醒、宠物名牌（头像+名字）、时钟/日期、同步状态角标；
- 数据来自同步快照，按 `servedPetId` 过滤；
- 右上角设置按钮 → 宠物端设置页：**修改 App 模式（宠物端 / 主人端）**、重新配对、屏幕常亮开关、服务器地址。

### 3.2 保活策略

| 能力 | 鸿蒙 | Android | iOS |
|---|---|---|---|
| 屏幕常亮 | `window.setWindowKeepScreenOn` | `FLAG_KEEP_SCREEN_ON` | `isIdleTimerDisabled` |
| 后台驻留 | 长时任务 ContinuousTask（需 `ohos.permission.KEEP_BACKGROUND_RUNNING`） | 前台服务 | 不做 |

统一经 method channel 暴露给 Dart。连接层：WebSocket 心跳 + 指数退避重连，恢复前台强制全量刷新。

## 4. 爱宠页副标题（需求 4）

`petnote_pages_pets.dart` PageHeader subtitle：

## 5. 远程视频入口（需求 5）

- 爱宠页 `PageHeader` 标题右侧加「远程视频」胶囊按钮；
- 点击弹底部选项 sheet：**视频通话**（双方开摄像头+麦克风）/ **先看看它**（仅宠物端开摄像头+麦克风，主人端静默观看）；
- 本期点击选项后进入占位页：展示配对设备在线状态 +「实时画面功能即将上线」；
- 协议包本期即定义信令消息：`call_invite` / `call_answer` / `call_reject` / `call_end` / `ice_candidate`，载荷含 `mode: call | watch`，下期 WebRTC 直接对接。

## 6. 测试与验证

- 遵守项目纪律：只定向跑新增/受影响的测试文件（禁止全量 `flutter test`）；不操作真机，客户端验证止于三端构建成功，由用户在模拟器实测。
- 协议包与服务器为纯 Dart：完整单元测试 + 本地起服务、两个内存客户端跑配对/同步集成测试（可闭环验证）。
- 客户端新增 widget 测试：角色选择页路由、副标题三态、视频按钮与选项 sheet、看板组件渲染（用内存 store/假同步数据）。

## 7. 风险

1. **鸿蒙保活**（最大不确定点）：ContinuousTask 权限与 ets 原生实现需真机/模拟器验证；
2. 鸿蒙 WebSocket：走纯 Dart `dart:io`，预期低风险，需构建验证；
3. flutter_webrtc 鸿蒙适配：**二期**风险，本期仅协议预留，不阻塞；
4. 隐私文案：启用同步后「数据全本地」承诺需要措辞更新，实施时与用户确认文案。

## 8. 二期计划（WebRTC 视频实体功能）

目标：「视频通话」与「先看看它」两种模式的真实跨网音视频，全链路开源自建，无付费 SDK。

### 8.1 技术栈

- **客户端**：`flutter_webrtc`（开源插件）——摄像头/麦克风采集、编解码、P2P 传输；
- **信令**：复用本期服务器的 WebSocket 通道与已定义的信令消息（`call_invite` / `call_answer` / `call_reject` / `call_end` / `ice_candidate`，`mode: call | watch`）；
- **NAT 穿透**：公共 STUN + 自建 coturn（本期 docker-compose 已预留编排），TURN 凭证由服务器按短期有效期下发。

### 8.2 实施步骤

1. **Spike：鸿蒙端 flutter_webrtc 适配验证**（最先做，决定平台矩阵）：用 OpenHarmony-SIG 适配仓库做最小构建 + 采集渲染验证；若不可用，降级方案为鸿蒙端暂不支持视频（仅 Android/iOS 主人端 ↔ Android 宠物端），或宠物端 MJPEG 帧流兜底；
2. **服务器**：启用信令转发（消息定义本期已就位）、coturn 接入与凭证下发接口；
3. **主人端 UI**：呼出等待页、通话页（远端画面、静音、挂断、切换前后摄像头）、「先看看它」观看页（无本地上行）；
4. **宠物端**：看板内来电处理——`call` 模式自动接听（可在宠物端设置中关闭）、`watch` 模式静默推流（不渲染主人端画面、不播放主人端音频）；
5. **权限**：三端摄像头/麦克风权限申请，复用现有 `permission_request_gate` 模式；
6. **弱网与异常**：ICE 断线重连、通话中暂停数据同步避免带宽竞争、通话结束恢复。

### 8.3 验收标准

两台设备（模拟器或用户真机）跨网完成：① `call` 模式双向音视频；② `watch` 模式单向监看（主人端不开摄像头/麦克风）；③ 挂断/拒接/超时未接全部正确回到原页面。

### 8.4 二期风险

1. flutter_webrtc 鸿蒙适配成熟度（spike 前置解决）；
2. TURN 中继流量走自有 VPS 带宽，监看场景长时间使用需关注带宽占用（可在设置中限制分辨率/帧率）。
